# data-subject 차별화 방향과 개선 로드맵

작성일: 2026-10-11. 구현 기준: `@nestarc/data-subject@0.2.0`, 저장소 커밋 `92a05cb`. 대상 독자: 패키지 유지보수자와 도입을 검토하는 개발팀.

**제품의 중심을 NestJS 애플리케이션의 개인정보 처리 정책과 실행 검증에 둔다.** 개발팀이 데이터 내보내기·삭제를 구현하고, 스키마 변경 후에도 정책 누락과 잘못된 처리를 발견하며, 실행 범위와 결과를 설명할 수 있도록 한다. 무료 실행 코어를 유지하고 도입 지원·유지보수·nestarc 공동 지원의 지불의사를 검증한다. 초기 투자 범위는 4주이며, 실제 도입 결과에 따라 8~12주까지 확장한다.

이 문서는 차기 제품 우선순위를 제안한다. 아래 API 이름, 일정, 완료 기준은 향후 목표이며 현재 제공 기능을 뜻하지 않는다. 기존 [PRD](./prd.md)의 시장 가정과 버전별 로드맵보다 이 문서의 제품 우선순위를 우선한다. 현재 동작은 [README](../README.md)와 소스를 기준으로 하고, [0.2 기술 사양](./data-subject-0.2.0-spec.md)은 당시 설계 자료로 참조한다.

**시장 근거는 요청 처리량보다 구현과 유지보수 비용을 먼저 줄이는 방향을 지지한다.**

| 확인한 근거 | 해석과 제품 결정 |
| --- | --- |
| EDPB의 2025년 조사에는 764개 조직이 응답했고, 약 70%가 삭제 요청을 연간 10건 미만 받았다. 공공·민간이 섞인 표본이다. [2026 보고서 p.8~10](https://www.edpb.europa.eu/system/files/2026-02/edpb_cef-report_2025_right-to-erasure_en.pdf) | 모든 스타트업에 고빈도 자동화 수요가 있다고 가정하지 않는다. 최초 구현 시간과 스키마 변경 대응 시간을 측정한다. |

| npm 공식 집계에서 2026-09-10~10-09 다운로드는 11회다. [고정 기간 통계](https://api.npmjs.org/downloads/point/2026-09-10:2026-10-09/@nestarc/data-subject) | 고객 수나 지불의사로 환산하지 않는다. 기능 확장 전에 실제 스키마 도입과 반복 사용을 확인한다. |

기존 PRD의 “상용 제품은 월 수천 달러”, “OSS 시장은 비어 있다”, “기업 실사에서 TOP 3 문제”는 이번 우선순위의 근거로 사용하지 않는다. 절감액은 고객의 실제 작업시간으로 계산한다. 개인정보 관리 소프트웨어 전체 시장 규모를 이 SDK의 시장 규모로 환산하지 않는다.

**첫 고객은 자신의 데이터 구조와 보존 예외 때문에 삭제 구현이 복잡한 개발팀이다.**

| 우선순위 | 고객 조건과 도입 계기 | 검증할 가치 |
| --- | --- | --- |
| 첫 대상 | NestJS·Prisma를 사용하며 여러 테이블에 사용자 데이터가 있고, 인보이스·감사 로그 등 보존 예외가 있는 팀. 최근 실제 요청 또는 고객 실사를 경험함 | 직접 작성한 SQL·서비스 코드보다 구현·리뷰·변경 대응 시간이 줄어드는가 |
| 두 번째 대상 | Transcend·Osano 등 요청 관리 제품을 쓰면서 내부 애플리케이션 연결을 개발하는 팀 | 플랫폼별 처리 코드를 다시 쓰지 않고 기존 정책을 재사용하는가 |
| 유통 경로 가설 | tenancy·audit-log·outbox 등 nestarc 구성요소를 검토하거나 사용하는 팀 | 검증된 조합과 예제로 설치·트랜잭션 연결 비용이 줄어드는가 |
| 초기 제외 | 테이블이 적고 요청·실사 경험이 없는 서비스, 운영 포털과 다수 SaaS 연결을 즉시 요구하는 조직 | 무료 예제로 지원하되 개별 요구에 맞춘 범용 플랫폼 개발을 시작하지 않음 |

사용자는 백엔드 엔지니어이고, 도입 결정자는 기술 리드 또는 CTO라는 가설로 인터뷰한다. 보존 규칙과 요청 승인 조건은 고객의 담당자가 제공한다. 첫 고객 조사에서 역할과 예산 소유자가 다르면 판매·지원 방식도 수정한다.

**약속할 가치는 정책의 변경 관리, 실행 결과의 신뢰성, 기존 시스템과의 연결이다.**

| 차별화 축 | 고객에게 약속할 결과 | 비교·검증 방법 |
| --- | --- | --- |
| 정책과 스키마의 일치 | 필드 추가·이름 변경·보존 정책 변경 시 처리 누락 후보를 CI에서 확인 | 파일럿의 실제 스키마 변경 및 합의한 결함 fixture에서 발견·오탐·수정 시간을 기록 |
| 실행 전후의 확인 | 삭제·치환·보존될 범위를 미리 보고, 실행 후 등록된 범위의 결과를 확인 | dry-run의 변경 0건, 다른 테넌트 변경 0건, 의도적으로 실패한 executor 검출 |
| 운영 중 재사용 | 동일 요청 재전송과 증빙 저장 실패를 구분하고 처리 내역을 재조회 | 실제 PostgreSQL에서 동시 요청·프로세스 중단·증빙 업로드 실패를 주입 |
| NestJS 도입 편의 | 자신의 인증·DB·작업 큐를 유지하면서 실행 코어를 연결 | 깨끗한 프로젝트와 고객 프로젝트에서 설치부터 첫 검증 성공까지 작업시간 측정 |

`delete/anonymize/retain`, ZIP, SHA-256은 기본 기능이다. 장기적인 차별화는 실제 스키마에서 축적한 검증 사례, 호환성 보장 범위, 운영 장애 처리 계약에 둔다. SHA-256은 저장한 바이트를 대조하는 수단이며, 독립 서명이나 실행의 진실성·변경 불가능성을 보장하지 않는다. 제품 설명은 “GDPR/CCPA 준수 보장” 대신 실제로 검증한 동작과 범위를 사용한다.

**P0는 도입과 실행의 기본 신뢰를 확보한다.** P0 완료 전에는 파일럿에서 합성 데이터나 고객이 승인한 테스트 데이터만 사용한다. 현재 코드를 곧바로 안전한 운영 경로라고 홍보하지 않는다.

| ID | 개선 항목 | 최소 범위와 완료 기준 | 의존성 |
| --- | --- | --- | --- |
| R1 | 지원 조합과 도입 예제 | 기존 NestJS 10·Prisma 5 회귀 확인. 파일럿이 사용하는 NestJS major 1개·Prisma major 1개·Node LTS 1개를 대표 조합으로 고정하되 Prisma 7을 우선 검토. 설치된 npm tarball로 PostgreSQL export/erase/retain/rollback 검증. 지원표에 정확한 버전과 제외 조합 기록 | 없음 |
| R2 | 테넌트와 호출 계약 | multi-tenant 모드에서 tenant metadata 누락·빈 ID를 실행 전에 거절. 명시적 single-tenant 경로 제공. 요청 조회도 tenant 조건 사용. 예제의 인증·권한 검사와 주체 확인 연결. 두 테넌트에 같은 subjectId가 있어도 다른 테넌트의 행·요청·파일에 접근하지 못함 | R1 |
| R3 | 실패와 완료 의미 정리 | 생성 이벤트 실패, DB 실패, 증빙 업로드 실패, 완료 콜백 실패를 구분하는 상태 계약과 회귀 검증. 확정된 데이터 변경을 콜백 오류만으로 미실행처럼 표시하지 않음. 기존 감사 이벤트는 유지하고 실패 단계·복구 가능 여부를 추가 | R1 |

R2에서 패키지는 자체 인증 서비스를 만들지 않는다. 호출자가 인증·주체 확인을 완료한 사실과 actor를 전달하는 경계를 정의하고, 실제 확인은 애플리케이션이 맡는다. Export에는 삭제 정책과 구별되는 명시적 출력 필드 목록을 두어 비밀번호 hash·토큰 등 요청에 포함하면 안 되는 값을 제외한다. 등록하지 않은 민감 필드가 응답 ZIP에 들어가지 않는지 fixture로 확인한다. R3의 상태 계약은 다음 단계의 저장 모델·마이그레이션보다 먼저 결정한다.

**2026-10-11 P0 구현 상태 — 미배포 작업 트리.** 아래는 합성 데이터로 검증한 기술 범위이며 고객 파일럿 참여·운영 도입·출시를 뜻하지 않는다.

| 항목 | 구현 및 확인 결과 |
| --- | --- |
| R1 | Nest 10.4.22 / Prisma 5.22.0 및 Nest 11.2.7 / Prisma 7.10.0, Node 24.11.1에서 실제 npm tarball 설치·생성된 타입 컴파일·Nest 초기화·PostgreSQL export/erase/retain/rollback 통과. [지원 조합과 재현 방법](compatibility.md) |
| R2 | 명시적 tenant scope와 single-tenant 모드, 빈 ID 거절, tenant별 요청·파일 조회, exportFields 허용 목록, 인증·권한·주체 확인 호스트 예제 및 두 tenant/같은 subject 회귀 테스트 구현 |
| R3 | 생성·처리·DB·artifact·상태 저장 실패 단계와 실행 결과 기록, 실행 전 unknown 영속화, commit 후 완료 콜백 실패 분리, 저장소 장애 시 요청 ID가 포함된 복구 오류 구현 |

기존 호출부는 [P0 이전 안내](p0-migration.md)를 적용해야 한다. 당시 P1의 필드 검증·idempotency·증빙 재시도는 미구현이었으며, 아래 P1 구현 상태가 현재 진행 상황이다. `recovery` 값만으로 데이터 실행이 자동 재개되지는 않는다. 고객이 실제 사용하는 조합과 스키마의 검증은 파일럿 단계에서 추가한다.

**P1은 자체 구현보다 선택할 이유를 만든다.** R4~R7을 하나의 파일럿 흐름으로 연결한다. 구현 가능한 엔티티와 DB 범위를 명시하고, 지원 밖의 동작은 실행 전에 거절하거나 명시적 사용자 실행기로 위임한다.

| ID | 개선 항목 | 최소 범위와 완료 기준 | 의존성 |
| --- | --- | --- | --- |
| R4 | 변경을 쓰지 않는 실행 미리보기 | 행 원문 없이 삭제·치환·보존 계획, 예상 행 수, 정책 hash, 검사 시각을 반환. 동일한 정책 컴파일 결과를 실행과 공유. dry-run은 업무 DB 변경·외부 삭제 호출 0건. 실행 시 tenant·subject·정책 버전과 선행 조건 재검증. 만료·정책 변경 시 재계획 요구 | R2, R3 |

R4의 예상 행 수는 영구 스냅샷 약속이 아니다. 최초 파일럿은 제한된 크기의 단일 DB 작업으로 한정하고 실행 직전 트랜잭션 안에서 범위를 다시 확정한다. 범위 변경을 허용할지 재승인을 요구할지는 명시적 설정과 증빙으로 남긴다.

R5는 먼저 공유 정책과 신규 필드 누락 검사를 제공한다. 관계·순서·보존 충돌 검사는 5~8주 범위로 두고 사용자가 선언한 관계를 대상으로 제한한다. 임의의 관계 그래프를 자동 탐색해 삭제하지 않는다. R6는 기술적 치환·보존 결과를 검증하며 재식별 불가능성이나 미등록 저장소까지 판정하지 않는다.

R7은 단일 PostgreSQL 경로부터 제공한다. 트랜잭션에 참여하지 않는 custom executor에는 동일한 원자성을 약속하지 않는다. 외부 저장소는 DB와 원자적으로 commit되지 않으므로 증빙 생성에 필요한 최소 결과를 DB에 보존하고, 비공개 저장소의 결정적 key에 업로드 후 최종 완료를 기록한다. 재시도 후 동일 artifact를 확인할 수 있어야 하며, 외부 전송은 중복 가능성을 처리한다. 임의의 분산 단계 재개나 exactly-once는 이 범위에 포함하지 않는다.

P1 파일럿에는 비공개 S3 호환 저장소 예제 하나를 포함한다. `artifactUrl`을 공개 다운로드 링크로 취급하지 않고 인증된 조회와 짧은 만료 링크를 구분한다. export와 삭제 증빙의 보존기간은 각각 고객이 설정하고, 만료·삭제·실패 업로드 정리 절차를 검증한다. 원본 데이터 보존기간과 증빙 보존기간을 같은 설정으로 묶지 않는다.

| 실행 신뢰성 | 실제 DB에서 다른 tenant, no-op executor, 중복 실행, commit/업로드/통지 실패를 주입 | 다른 tenant 변경 0건, 합의한 잘못된 성공 판정 0건. 미검증 경로는 지원표에서 제외 |

| 지불의사 | 가격·범위·지원 시간을 포함한 제안 후 실제 유료 파일럿/계약 확인 | G3까지 1건. 구두 관심·다운로드·GitHub star는 매출로 집계하지 않음 |

추적은 고객 동의하에 인터뷰와 익명 집계로 시작한다. 패키지에 자동 외부 텔레메트리를 추가하지 않는다. 요청 수·데이터 건수와 엔지니어링 시간을 구분하고, 규제 벌금 회피액을 예상 매출·절감액에 넣지 않는다.

**확장은 확인된 반복 수요에 따라 선택한다.** 관리 포털, 다수 SaaS 커넥터, 범용 ORM 지원, 자동 법률 판단, 보존기간 자동 삭제, 백업 복원 후 재삭제, identity graph는 현재 투자 범위 밖이다. 데코레이터·CSV 포맷도 도입 실패의 반복 원인으로 확인될 때 우선순위를 높인다. 공개 코드와 예제만으로 충분한 사용자는 무료로 유지하고, 복잡한 조합 검증과 운영 지원에 예산이 있는 팀을 대상으로 유료 가설을 검증한다.

출시 시점에는 기존 custom storage/executor 사용자에 대한 영향, 요청·증빙 schema migration, 지원 종료·호환 경로를 함께 문서화한다. API 변경을 단순 peer range 확대나 optional field 추가만으로 해결했다고 간주하지 않는다. 현재 `0.x` 개발 단계에서 호환되지 않는 API 변경과 P1·P2 기능 추가를 구분하도록 차기 버전을 `0.3.0`으로 결정했다. 필수 격리·검증 기능은 무료 코어에 포함하고, 유료화는 도입 작업·지원 범위·유지보수 책임을 대상으로 검증한다.
